# 開発パイプライン俯瞰評価（2026-08-08）

**目的**: 「このCI/CD体制は客観的に見て妥当か。何が揃い、何が欠け、どれを直すべきか」に、
公開フレームワークを物差しとして答える。個別改善の積み上げではなく全体地図。

**評価対象**: sinoda1114 の全リポジトリ運用（標準CI = ci-standard、sweeper、ブランチ保護、
AIレビューボット4種、および周辺の開発運用全体）。

---

## 1. 物差しの選定と、この文脈への適合調整

| フレームワーク | 何を測るか | 採用理由と調整 |
|---|---|---|
| **DORA**（4キーメトリクス＋能力群） | デリバリー性能: デプロイ頻度 / 変更リードタイム / 変更失敗率 / 復旧時間(MTTR) | 業界標準。ただし2026年版の知見で「AI時代は個人生産性が組織成果と乖離する」「**レビュー無しマージの増加**が品質リスク」「**MTTRが最も信頼できる指標**」とされており、ソロ＋AIエージェント並列という当環境にそのまま刺さる |
| **SLSA v1.1**（Build Track L0〜L3） | サプライチェーン保全: ビルドの来歴（provenance）と改竄耐性 | npm供給網対策を重視する方針と直結。ただしL3は成果物を外部配布する組織向けで、ソロの内製アプリには過剰と判定 |
| **OWASP DSOMM**（6次元×5レベル） | DevSecOps全体の網羅性チェック | 「見落としている領域はないか」の網羅用。組織文化系の項目はソロに不適合のため除外し、技術次元のみ使用 |

ソロ＋AIエージェント並列環境向けの重み付け: **「人間の記憶に依存しない強制」**を最重要視
（普通のチームなら「文化・教育」で担保する部分を、この環境では全て仕組みで代替する必要があるため）。

---

## 2. 評価結果（軸ごとの現在地）

凡例: ◎ 業界水準以上 / ○ 妥当 / △ 部分的 / ✗ 欠落

| # | 軸 | 評価 | 現在地の根拠 | 世間水準との差 |
|---|---|---|---|---|
| 1 | ビルド/テスト自動化 | **◎** | 標準CI（lint/typecheck/test/build/audit/e2e）を36リポジトリに統一。構成自動判定・冪等・sweeperで自動維持。新規リポジトリも翌朝までに自動適用 | 中央管理Reusable Workflow＋自動配布は中規模組織でも未整備が多い。**水準超え** |
| 2 | 品質ゲートの強制力 | **○** | public 27リポジトリにブランチ保護（CI必須・会話解決必須・admin含む）。PR #40で全鎖を実証済み | 残: private 9リポジトリは Free プラン制約で保護不可（→ロードマップ） |
| 3 | サプライチェーン | **○** (SLSA L1相当) | lockfileコミット・npm ci・ignore-scripts・audit high・Dependabot・action SHA固定・secret scanning＋push protection・Socket(public) | SLSA L2（署名付きprovenance生成）は未実施だが、**成果物を外部配布していないため現状不要**。npm公開を始めたら要再評価 |
| 4 | コードレビュー | **◎** | AIボット4種＋裁定ポリシー明文化＋会話解決ゲート。2026年DORAが警告する「レビュー無しマージ」(31%増) を構造的に防止済み | AI時代のレビュー体制としては先行。残: Copilot死蔵の整理のみ |
| 5 | **デプロイ (CD)** | **✗** | 手動デプロイ（wrangler / vercel CLI）、リポジトリごとにバラバラ、マージ＝本番反映の一本化なし、ロールバック手順なし | **最大のギャップ**。DORAの根幹「デプロイ自動化」が欠落。CIは標準化されたがCDは未着手 |
| 6 | **監視・運用 (Observability)** | **✗** | 本番アプリの死活監視・エラー通知・ログ集約が実質なし。障害は「気づいたら」ベース | **第2のギャップ**。MTTRは「最も信頼できる指標」だが、そもそも障害を検知できない＝復旧が始まらない |
| 7 | シークレット管理 | **△** | 基盤ダッシュボード正本・push protection有効は良。ただし sweeper PAT が無期限、ローテーション方針なし | 期限設定＋失効時の再発行手順だけ整えれば ○ |
| 8 | 復旧・ロールバック | **△** | git revert 可能、スキーマ変更は人間承認ルール有り。ただしデプロイのロールバック手順は未定義（軸5に依存） | 軸5解消とセットで自然に改善する |

**総評**: 「コードがmainに入るまで」（軸1〜4）は業界水準以上に到達。
**「mainに入った後」（軸5〜6, デプロイと監視）がほぼ空白**で、ここが構造的な弱点。
今日までの作業はパイプラインの前半分を完成させた、が正確な現在地。

## 3. ロードマップ（やる / やらない を明記）

### やる（優先順）

| 優先 | 項目 | 理由 | 規模 |
|---|---|---|---|
| 1 | **デプロイ標準化**: 「mainマージ＝自動デプロイ」への一本化（Cloudflare/Vercel系は git連携、それ以外は deploy workflow 標準をci-standardに追加） | 軸5。DORAの根幹欠落の解消。手動デプロイ忘れ（nozei-scheduleで既知の事故パターン）を構造的に排除 | 中 |
| 2 | **最小限の監視**: 本番アプリに死活監視＋エラー通知（UptimeRobot等の無料枠 or CF/Vercelの標準機能） | 軸6。「気づける」だけでMTTRが桁で変わる | 小 |
| 3 | **Copilotレビュー整理**: 有効化 or Reviewersから外す | 軸4の残タスク。死んだ設定の放置は誤解のもと | 極小 |
| 4 | **sweeper PAT に期限設定**＋失効時の再発行手順をREADMEに明記 | 軸7 | 極小 |
| 5 | **カバレッジ閾値を本番系リポジトリへ展開**（テスト資産があるリポジトリのみ） | 軸1の仕上げ。テストが無いリポジトリには無意味なので対象を絞る | 小 |
| 6 | **private リポジトリの保護**: GitHub Pro（$4/月）加入 or 本番系のpublic化の判断 | 軸2の残。sweeperが毎日再試行しているため、加入した瞬間に自動適用される | 判断のみ |

### やらない（ソロ運用には過剰と判定）

| 項目 | 判定理由 |
|---|---|
| SLSA L2/L3（provenance署名・ビルド隔離強化） | 成果物を外部配布していない。npmパッケージ公開を始めたら再評価 |
| DSOMM高成熟度の組織項目（教育・複数チーム統制） | ソロに該当なし。「仕組みによる強制」で代替済み |
| Visual regression 自動化 | ベースライン画像の運用コストが利益を上回る。スクショ添付ルールで十分 |
| バンドルサイズ回帰CI | 現アプリ規模で問題が発生していない。発生してから導入 |
| DORAメトリクスの計測ダッシュボード | ソロでは計測より改善実行が先。2026年版DORA自身が「AI時代はスループット指標が価値と乖離」と警告 |
